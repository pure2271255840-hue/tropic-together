# Tropic Together Phase 1 工作流依据

状态：Phase 1 后续执行依据。

最后更新：2026-07-25。

## 1. 产品定位

Tropic Together Phase 1 是一个给朋友旅行前和旅行中使用的私密协作工具。

第一周目标不是商业化，不做完整平台化，不做内嵌地图系统。目标是在旅行前快速完成：

- 拉一个旅行计划群组。
- 大家一起添加想去的地点。
- 大家对地点投票和写原因。
- AI 基于透明投票公式生成可编辑行程草稿。
- 大家对行程版本投票。
- 发起人确认最终版。
- 旅行当天首页能看到今天计划和下一个即将执行的安排。

核心原则：

- 地点和行程要区分，但都隶属于同一个旅行计划。
- 地点投票回答“这个地方值不值得进计划”。
- 行程投票回答“这个安排是否合理、时间是否顺、大家是否接受”。
- AI 只生成草稿和优化建议，不做最终决策。
- 最终版由发起人确认。
- 最终版确认后，AI 不再参与，后续由发起人手动修改。
- 不接 Google Maps API 或 Apple MapKit JS。
- 每个地点和每版行程只生成 Apple Maps / Google Maps 外部 URL。
- 地图 URL 失败不能阻断地点、投票、备注、行程查看。

## 2. 核心对象

### 2.1 旅行计划群组

旅行计划群组是产品的最高协作单位。

示例：

```text
亚庇三天计划
槟城 x 哥打京那巴鲁 10 天计划
```

字段建议：

- 计划名称
- 发起人 / 旅行计划负责人
- 成员列表
- 日期范围
- 时区
- 酒店地址，可选
- 按日期设置酒店地址，可选
- 当前阶段
- 邀请链接

发起人权限：

- 创建计划。
- 修改计划基本信息。
- 进入下一阶段。
- 触发 AI 生成行程草稿。
- 编辑行程草稿。
- 确认最终版。
- 最终版确认后继续手动修改。

普通成员权限：

- 加入计划。
- 添加地点。
- 对地点投票和写原因。
- 查看 AI 草稿。
- 对行程版本投票和写原因。

### 2.2 地点池

地点池是某个旅行计划下面的候选地点列表，不是全局地点库。

用户不是进入一个抽象地点系统，而是进入：

```text
亚庇三天计划 -> 添加地点 -> 地点投票 -> 生成行程草稿
```

地点字段建议：

- 地点名称
- 城市 / 区域
- 地址，可手填
- 地点备注
- 预计停留时间，可选
- 添加人
- 初始标签
- Apple Maps URL
- Google Maps URL
- 当前投票分数
- 当前排名

地点初始标签：

- 一定要去
- 还不错

地点投票：

- 点赞
- 倒拇指
- 投票原因，可选但强烈建议

地点投票原因示例：

- 想去
- 太远
- 排队可能久
- 顺路可以去
- 不适合当天节奏

### 2.3 行程版本

行程是把地点池里的地点安排到具体日期和时间段后的结果。

行程版本示例：

```text
草稿 v1
草稿 v2
最终版 v1
最终版 v2
```

行程版本字段建议：

- 所属旅行计划
- 版本号
- 版本状态
- 生成来源：AI 生成 / 手动编辑
- 创建人
- 创建时间
- 每日行程
- 本版行程投票
- 本版地图 URL

行程项字段建议：

- 日期
- 开始时间
- 结束时间
- 地点
- 标题
- 备注
- Apple Maps URL
- Google Maps URL
- 是否锁定

行程投票：

- 对整版行程投点赞 / 倒拇指
- 投票原因
- 后续可以扩展为对某一天或某个行程项投票，但 Phase 1 优先整版行程投票

## 3. 阶段流转

每个旅行计划都有明确状态。用户进入首页时，不需要猜自己该做什么，首页行动卡片直接告诉用户下一步。

建议状态：

```text
setup
collecting_places
place_voting
draft_ready
itinerary_voting
final_confirmed
travel_active
```

中文展示：

```text
设置计划中
收集地点中
地点投票中
可生成行程草稿
行程投票中
已确认最终版
旅行进行中
```

### 3.1 设置计划中

发起人创建计划。

必须设置：

- 计划名称
- 日期范围

可选设置：

- 酒店地址
- 每日酒店地址
- 简短说明

完成后生成邀请链接。

首页行动卡片：

```text
计划还在设置中
[设置日期和酒店] [复制邀请链接]
```

### 3.2 收集地点中

成员加入后可以添加地点。

地点添加后系统生成：

- Apple Maps URL
- Google Maps URL

首页行动卡片：

```text
现在先收集想去的地点
已有 8 个地点，4 人参与
[添加地点] [查看地点池]
```

### 3.3 地点投票中

大家对地点池投票。

用户怎么知道该投票：

- 首页显示“你还有 N 个地点未投票”。
- 地点页默认显示“待我投票”。
- 地点页顶部显示当前投票进度。
- 手机底部“地点”图标可以显示待投票数量。

首页行动卡片：

```text
地点投票中
你还有 5 个地点没投票
当前最高分：丹绒亚路海滩
[去投票]
```

### 3.4 可生成行程草稿

地点投票达到最低条件后，发起人可以生成 AI 草稿。

最低条件建议：

- 至少 3 个地点
- 至少 2 名成员参与投票，或发起人手动跳过
- 发起人点击生成

首页行动卡片：

```text
地点投票已足够，可以生成行程草稿
[生成 AI 草稿]
```

### 3.5 行程投票中

AI 生成草稿后，进入行程投票。

大家看的是具体版本，例如：

```text
草稿 v1
```

用户怎么知道该投票：

- 首页显示“草稿 v1 等待你的意见”。
- 行程页顶部显示“你还没有对本版行程投票”。
- 手机底部“行程”图标可以显示待投票数量。

首页行动卡片：

```text
草稿 v1 等待确认
你还没有投票
[查看行程并投票]
```

如果有人倒拇指，需要写原因。发起人可根据原因修改草稿并保存为下一版。

### 3.6 已确认最终版

当大家同意，或发起人决定收口，发起人确认最终版。

关键规则：

- AI 不再参与最终版之后的修改。
- 最终版由发起人确认，不由 AI 重新生成。
- 最终版仍允许大家查看和投票反馈。
- 发起人可手动修改最终版，修改后形成新版本。

首页行动卡片：

```text
最终版已确认
今天 17:20 去丹绒亚路海滩
下一个计划：19:30 晚餐
[打开导航]
```

### 3.7 旅行进行中

首页转为执行视角：

- 今天计划
- 下一个即将执行的计划
- 外部导航按钮
- 临时改动入口

## 4. 投票公式

Phase 1 使用简单透明公式，方便用户理解。AI 不能黑箱决定地点是否进入草稿。

建议初版公式：

```text
一定要去 = +3
还不错 = +1
点赞 = +2
倒拇指 = -2
```

地点得分：

```text
地点分 = 标签基础分 + 所有成员投票分
```

地点分区：

```text
高优先级：分数 >= 5
可顺路安排：分数 2 到 4
争议地点：至少 2 个倒拇指，或点赞和倒拇指同时较多
暂不安排：分数 < 2
```

这些阈值后续可以调整，但 Phase 1 先保持透明。

地点列表排序：

1. 高优先级
2. 可顺路安排
3. 争议地点
4. 暂不安排

同一分区内按分数从高到低排序。

## 5. AI 的职责边界

AI 可以做：

- 根据地点池、日期、酒店地址、投票分数、投票原因、预计停留时间生成行程草稿。
- 给出每天的建议顺序。
- 给出为什么这样安排。
- 提醒明显冲突，例如某天太满、地点跨度太大。
- 在发起人要求时基于人类修改生成新草稿版本。

AI 不做：

- 不决定最终版。
- 不绕过成员投票。
- 不修改最终版。
- 不负责真实地图路线准确性。
- 不获取或保存地图 API key。
- 不读取不必要的隐私文件、票据、护照、完整订单号。

AI 输入只能包含最小必要结构化数据：

- 日期范围
- 酒店地址
- 地点名称、地址、备注、预计停留时间
- 地点投票分数和原因
- 成员匿名标签
- 已有行程草稿

最终确认规则：

```text
AI 生成草稿 -> 人修改草稿 -> 大家投票 -> 发起人确认最终版
```

不要做：

```text
大家同意 -> AI 再生成最终版
```

原因：大家刚同意后，AI 如果再次改写，会制造新的不确定性。

## 6. 地图 URL 规则

不接内嵌地图。

每个地点生成：

- Apple Maps URL
- Google Maps URL

每个行程项生成：

- 到该地点的 Apple Maps 导航 URL
- 到该地点的 Google Maps 导航 URL

每一版行程可以附：

- 每天第一站的导航 URL
- 每个行程项的导航 URL
- 后续可扩展为多点路线 URL，但 Phase 1 不强依赖

URL 失败处理：

- 不显示阻断错误页。
- 保留地点和行程内容。
- 用户可复制地址自行打开地图。

## 7. 手机端信息架构

Phase 1 以手机观感为主。

底部导航固定为：

```text
首页
行程
地点
```

顺序要求：

1. 第一个图标是首页。
2. 第二个是行程。
3. 第三个是地点。

不要在底部导航放太多入口。任务、文件、费用、AI 设置都不进入 Phase 1 底部主导航。

### 7.1 首页

首页负责告诉用户“现在该做什么”。

主要模块：

- 当前计划状态
- 当前行动卡片
- 今天计划
- 下一个即将执行的计划
- 发起新计划按钮

首页根据阶段变化：

```text
收集地点中 -> 添加地点
地点投票中 -> 去投票
可生成行程草稿 -> 发起人生成 AI 草稿
行程投票中 -> 查看行程并投票
已确认最终版 -> 今天计划和下一个计划
```

### 7.2 行程页

行程页负责“安排怎么走”。

主要模块：

- 当前版本状态
- 草稿 / 最终版标识
- 版本列表
- 按日期分组的行程
- 每个行程项的地图 URL
- 整版行程投票
- 投票原因
- 发起人编辑入口
- 发起人确认最终版入口

### 7.3 地点页

地点页负责“哪些地方值得去”。

主要模块：

- 添加地点
- 待我投票
- 地点池
- 地点排名
- 地点标签
- 点赞 / 倒拇指
- 投票原因
- 争议地点区
- 暂不安排区

## 8. Supabase 数据模型方向

Phase 1 后端优先 Supabase。

建议表：

```text
profiles
travel_plans
plan_members
plan_hotels
places
place_votes
itinerary_versions
itinerary_days
itinerary_items
itinerary_votes
itinerary_vote_notes
```

关键关系：

- 一个 travel_plan 有多个 members。
- 一个 travel_plan 有多个 places。
- 一个 place 属于一个 travel_plan。
- 一个 place 有多个 place_votes。
- 一个 travel_plan 有多个 itinerary_versions。
- 一个 itinerary_version 有多个 itinerary_days。
- 一个 itinerary_day 有多个 itinerary_items。
- 一个 itinerary_version 有多个 itinerary_votes。

Auth 建议：

- 第一周优先匿名登录 + 昵称 + 邀请链接。
- 之后可绑定邮箱 magic link。

权限规则：

- 只有计划成员能读该计划。
- 只有计划成员能添加地点和投票。
- 只有发起人能进入下一阶段、生成 AI 草稿、确认最终版。
- 最终版确认后，只有发起人能修改最终版。

## 9. 当前前端实现状态

当前仓库已有一个 Phase 1 localStorage 技术底座，但它不是最终交互版本。

已经有：

- Next.js 前端基础。
- localStorage trip 数据层。
- 首页 / 地点 / 行程基础路由。
- 地点添加、编辑、投票、评论。
- 行程基础展示和添加。
- Apple / Google 外部导航 URL helper。
- 旧地图 POC 和旧 dashboard/mock 已清理。

需要下一轮重构：

- 把“地点状态 candidate/confirmed”改成“地点标签 + 地点投票分区”。
- 增加旅行计划阶段状态。
- 首页增加明确行动卡片。
- 地点页默认显示“待我投票”和排名。
- 行程页改成“行程版本”模型。
- 增加整版行程投票。
- 底部导航调整为：首页 / 行程 / 地点。
- 把 AI 入口放到发起人动作里，只在可生成草稿阶段出现。

## 10. 下一轮执行优先级

下一轮从 UI 和数据模型重构开始，不先接 Supabase。

建议顺序：

1. 更新 `features/trip/types.ts`，加入计划阶段、地点标签、地点投票原因、行程版本、行程投票。
2. 更新 seed data，让示例数据符合“亚庇三天计划/槟城 KK 计划”的真实工作流。
3. 重构首页为状态驱动行动卡片。
4. 重构地点页为“待我投票 + 排名 + 分区”。
5. 重构行程页为“版本 + 整版投票 + 发起人确认最终版”。
6. 保留外部地图 URL，不接地图 API。
7. 再进入 Supabase local。
