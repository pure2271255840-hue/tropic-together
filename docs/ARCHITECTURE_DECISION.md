# Architecture Decision

Status: documentation checkpoint. No application code, migrations, Auth logic, deployment configuration, or provider integration has been approved by this document alone.

## Decision Drivers

- Friends in mainland China must be able to use the product without a VPN.
- The future Expo iOS and Android clients must use the same backend contracts as the web app.
- Provider-specific SDKs, API keys, model names, map services, and deployment assumptions must stay outside product/domain logic.
- The current Vercel and Supabase setup can remain useful for prototype preview, but it must not become the only production path.

## Current Dependency Posture

| Dependency | Browser direct dependency | Replace behind adapter | Provider-agnostic code |
|---|---:|---:|---|
| Vercel | Yes, if the app is hosted there | Mostly deployment-level | Next.js routes/components, domain services, typed API contracts |
| Supabase Cloud | Yes if browser uses Supabase client/Auth endpoints directly | Partially; Postgres schema is portable, Supabase Auth/RLS/Storage are not fully portable | User/trip/member models, repositories, membership rules |
| Mapbox | Yes if Mapbox GL/tile APIs are loaded by the browser | Yes through MapProvider | Place, coordinate, route, bounds, marker, and itinerary data models |
| OpenAI | Should be no direct browser dependency | Yes through AIProvider | Planning request/response schema, prompt inputs, structured output validators |

## China-First Target Architecture

- Deploy Next.js on Alibaba Cloud ECS or a container platform, with Nginx as the public reverse proxy.
- Use a domestic PostgreSQL-compatible database such as Alibaba Cloud RDS PostgreSQL or PolarDB PostgreSQL.
- Use private Alibaba Cloud OSS buckets for files, accessed through permission-aware signed URLs generated by the backend.
- Use a mainland-accessible AI provider by default in China production, selected server-side through AIProvider.
- Use MapProvider so domestic map services can replace Mapbox without changing product data models.
- Keep browser clients pointed only at our own domain and typed API routes.

## AI Provider Architecture

### Server-Side Provider Selection

- AI providers are selected only on the server.
- Browser clients never receive provider API keys, provider base URLs, raw model names by default, or provider account details.
- Browser clients call our own typed backend AI API.

### OpenAI Eligibility

- Do not decide whether to use OpenAI based on VPN availability, client IP, or a user-facing provider toggle.
- Mainland China production defaults to a mainland-accessible provider.
- OpenAI can exist only in a separately configured global environment where account usage and access are compliant.
- OpenAI must not be the default or required provider for the China production environment.

### Provider-Agnostic Concepts

- `AIProvider`: server-side provider adapter with text, structured output, and optional future streaming methods.
- `AIModelProfile`: a server-side model capability and routing profile.
- `ModelRegistry`: a server-side registry that selects enabled model profiles by environment, mode, capability, fallback priority, latency tier, and cost tier.
- `generateText`: provider-agnostic text generation operation.
- `generateStructured`: provider-agnostic structured generation operation with schema validation.
- Future streaming support: optional server-side capability that must not change the non-streaming typed contract.
- Provider capability metadata: structured output support, vision support, latency tier, cost tier, environment availability, enabled status, fallback priority.

### User-Facing Modes

The product UI should expose product-level modes, not raw provider names by default:

- 国内稳定版
- 快速生成
- 深度规划
- 高质量规划, only where globally supported

Raw provider and model names may appear only in internal admin, diagnostics, or evaluation tooling.

### Server-Side Model Registry Fields

The registry should track fields similar to:

- `provider`
- `model`
- environment availability: `cn`, `global`
- structured output support
- vision support
- latency tier
- cost tier
- enabled status
- fallback priority

### China Production Default

- Use a mainland-accessible provider such as Qwen/DashScope as the default candidate.
- Keep other domestic providers replaceable through adapters.
- Do not commit to any provider SDK in domain logic.

### Global Environment

- OpenAI may be an optional provider behind the same abstraction.
- Enabling OpenAI must not change product data models, prompt schema, or frontend API contracts.

### Data Minimization

- AI itinerary planning receives only structured, necessary travel data.
- Do not send original flight tickets, hotel PDFs, booking references, passport data, full email addresses, raw uploaded documents, or unnecessary private notes to any AI provider.
- Use stable IDs, dates, times, places, preferences, constraints, and anonymized traveler labels instead of personally identifying raw text.

### Internal Evaluation

- Future internal tooling may run the same anonymized planning input against multiple providers.
- Compare structured-output validity, itinerary quality, latency, failure modes, and estimated cost.
- Evaluation tooling is internal only and is not part of the MVP user experience.

### Mobile Readiness

- Future Expo clients must call the same backend AI API as the web app.
- No mobile client should call an AI provider directly.

## Provider-Specific Details That Must Stay Isolated

- API keys, signing credentials, base URLs, request headers, SDK clients, retries, rate limits, billing metadata, model names, token accounting, and provider error codes.
- Provider-specific prompt quirks and response repair logic.
- Map provider tokens, tile endpoints, coordinate conversion details, geocoding/routing endpoint shapes, and attribution requirements.
- Storage bucket names, object signing credentials, private URL generation, and CDN details.

## Phase Boundaries

Phase 0 documentation only:

- Record China-first architecture decisions.
- Define provider-agnostic AI and map boundaries.
- Define typed backend contracts.
- List open product-owner decisions.

Later implementation phases:

- Add application types/interfaces.
- Add Auth/session implementation.
- Add database migrations.
- Add provider adapters.
- Add AI planning API routes.
- Add map rendering or route planning.
- Add internal evaluation tooling.

## Open Product-Owner Decisions

- Alibaba Cloud region, domain, ICP filing path, and whether mainland production must launch on a China mainland region or can start in Hong Kong/Singapore.
- First domestic AI provider candidate and fallback provider order.
- Whether MVP Auth should use email magic link, SMS, WeChat, or a hybrid.
- Whether the production database should use RLS-style database enforcement, application-level authorization, or both.
- Which domestic map provider should be primary for China users and which provider should cover Malaysia travel data best.
- Whether internal AI evaluation tooling is required before any user-facing AI feature.
