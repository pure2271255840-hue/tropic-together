# Tropic Together 产品优化整合方案

状态：待产品负责人确认后执行

最后更新：2026-08-20

本文档整合当前项目快照、已有 Phase 1 工作流文档、真实使用反馈，以及最近形成的产品和技术建议。

它是产品改版方案，不代表所有内容都立即实现。实施时必须按本文档的“纳入范围 / 可选范围 / 暂缓范围”推进，避免一次性把产品做成复杂的专业行程编辑器。

## 1. 产品目标

一句话目标：

> 帮一群懒得做攻略的人，把大家随手丢进来的地点，自动整理成每天能直接导航执行的轻量行程。

真正要降低的是四种成本：

- 添加地点的成本；
- 理解成员偏好和分歧的成本；
- 把地点安排到每天的成本；
- 旅行当天决定“下一步去哪”的成本。

产品不追求生成一份专业、完整、长篇的旅游攻略，而是追求：地点可靠、每天清楚、路线足够可信、打开就能执行。

## 2. 当前方案能解决什么

本轮改版可以直接改善：

1. 地点添加仍像填表，而不是搜索地点。
2. 官方地点名、地址、坐标和用户备注混在一起。
3. 10 天行程不容易快速定位某一天。
4. AI 只凭地址和直线距离判断路线。
5. 行程内容过长，用户不知道今天该看什么。
6. AI 生成前需要填写一大段自由文本。
7. 生成后只能整体阅读和手工调整，缺少简单的锁定、重新整理和调整顺序。

但本轮改版不能自动解决：

- 营业时间、临时闭店、预约和票务真实性；
- 抵达、离开、入住、固定预约等旅行硬约束；
- 历史手动地点和海外地点的完整 POI 修复；
- 成员是否知道有新变化；
- 旅行当天交通变化后的动态执行；
- 同一地点与“这次要做什么活动”之间的语义区分。

这些问题需要单独增加数据结构或产品功能，不能假设接入高德以后自动消失。

## 3. 改版范围决策

### 3.1 第一阶段必须纳入

#### A. 地点搜索和结构化保存

`/trip/[tripId]/places` 改为搜索优先：

1. 输入关键词；
2. 选择城市或使用行程目的地；
3. 展示 3–5 个官方候选；
4. 点选候选；
5. 自动保存官方地点名、地址、城市、坐标、POI ID 和分类；
6. 再补充成员态度、原因和预计停留时间。

保留折叠的手动添加：

- 找不到地点时可以继续添加；
- 手动地点明确显示“位置未确认”；
- 粘贴地图链接时保留原始链接；
- 地理编码只作为兜底，不能把地址反查结果伪装成官方商家名称。

#### B. 10 天单日执行视图

`/trip/[tripId]/itinerary` 默认显示：

- 横向日期条；
- 当前日或第一个未完成日；
- 当天地点顺序；
- 每段通勤时间；
- 预计停留时间；
- 当天路线入口；
- 冲突、太赶或位置未确认提示。

不要默认展开 10 天的完整长列表。完整内容、成员理由和管理操作放进详情或管理入口。

#### C. 最小真实路线能力

有可靠坐标的地点使用地图服务返回的距离和通勤时间；没有可靠坐标的地点只能显示估算或待确认。

AI 负责：

- 理解节奏、晚间安排等偏好；
- 生成标题、摘要和软性建议；
- 解释取舍。

地图服务和本地规则负责：

- 地点间距离和通勤时间；
- 路线顺序；
- 时间冲突校验；
- 是否太赶。

#### D. 简化 AI 入口

AI 生成前只询问少量高价值选项：

- 节奏：轻松 / 正常 / 紧凑；
- 交通：驾车 / 步行，公交后续增加；
- 晚间：正常结束 / 晚餐后结束 / 最后喝酒；
- 可选的短补充，限制长度。

只生成一个当前草稿。生成后直接进入草稿，不再让用户阅读一份完整的多日预览后再做二次确认。

#### E. 简单调整能力

保留或增加：

- 锁定活动；
- 调整当天顺序；
- 移动到另一天；
- 重新整理未锁定部分；
- 查看为什么这样安排。

移动端第一版可以先使用上移/下移按钮，之后再做真正拖拽。

### 3.2 可选纳入

这些功能有价值，但可以在核心链路验证后再做：

- 手动地点补全、确认和合并重复地点；
- 首页“下一步行动”卡片；
- 新地点、AI 草稿、路线冲突的未读提示；
- 每天酒店地址，而不是全程共用一个酒店；
- 出发前刷新当天路线；
- 跳过当天某一站并放回未安排地点；
- 旅行中只解锁某一天，而不是解锁整个最终版；
- 固定活动和不可移动时间块。

### 3.3 第一阶段暂缓

- 浏览器内完整地图画布；
- 地图/列表双视图；
- 百度、腾讯等多个地图供应商同时接入；
- 营业时间、门票、预订、天气和评分；
- 多个 AI 版本对比；
- 复杂专业行程编辑器；
- 自动跨城长途交通规划；
- 聊天、文件、费用、提醒和推送系统；
- 旅行结束后的复杂复盘系统。

## 4. 现有工作流的问题和优化方向

当前工作流大致是：

```text
创建行程
→ 添加地点
→ 地点投票
→ AI 生成
→ 行程投票
→ 最终确认
→ 全局锁定
```

这个流程过于正式，且让成员在地点页和行程页之间反复切换。

建议产品层面改成：

```text
创建基础信息
→ 收集箱：搜索地点并一键表态
→ 随时生成一个草稿
→ 查看某一天
→ 有异议再调整
→ 发起人确认
→ 出发前按天执行
```

### 4.1 具体工作流调整

- 添加地点时同时完成当前成员的“想去 / 不太想去”表态。
- 不等待所有成员投票，发起人达到最低地点数量后即可生成草稿。
- 地点投票是协作参考，不应该成为硬性流程关卡。
- 行程投票保留，但作为反馈而不是必须完成的阻塞状态。
- 首页不只展示状态名称，而是展示当前唯一最重要的下一步。
- 生成草稿后直接落到当前行程视图，不再增加多个版本选择负担。
- 最终确认表示“当前版本可执行”，而不是旅行中永远不能修改。

后端已有 phase 可以暂时保留，以兼容旧数据；前端不必把每个 phase 都表现成必须完成的步骤。

### 4.2 首页行动卡片

首页应该根据状态显示一个主要动作：

```text
还没有地点       → 添加第一个地点
有地点未表态     → 去完成表态
地点已经足够     → 生成草稿
有草稿待查看     → 查看今天的安排
有冲突           → 处理冲突
最终版已确认     → 打开今天路线
旅行进行中       → 去下一站
```

不要同时展示多个等权重按钮，让用户自己判断下一步。

## 5. 高德接入边界

### 5.1 技术边界

页面不直接调用高德，统一经过服务端适配层：

```text
页面
→ /api/maps/*
→ MapProvider
→ AmapProvider
```

建议能力接口：

```text
searchSuggestions(query, city)
resolvePoi(providerPoiId)
geocode(address)
reverseGeocode(coordinate)
routeMatrix(origins, destinations, mode)
route(origin, destination, waypoints, mode)
```

第一阶段只需要先实现：

- 输入提示；
- POI 详情；
- 路线距离和通勤时间。

高德只优先服务中国大陆行程。海外地点继续使用手动添加、原始地图链接和现有 fallback。

### 5.2 配置和安全

建议服务端环境变量：

```env
AMAP_WEB_SERVICE_KEY=
AMAP_ENABLED=true
AMAP_REQUEST_TIMEOUT_MS=3000
```

不使用 `NEXT_PUBLIC_` 前缀，不把 Key 放进浏览器 bundle、日志或 workspace。

第一阶段不加载高德 JS 地图 SDK，也不申请浏览器端地图 Key。当前目标是搜索和路线数据，不是内嵌地图渲染。

服务端接口应具备：

- 登录校验；
- 行程成员校验；
- 输入长度限制；
- debounce 和缓存；
- 超时降级；
- 基础限流；
- 供应商错误转成用户可理解的提示。

### 5.3 统一地点字段

在现有 `TravelPlace` 基础上增加可选字段，保持旧数据兼容：

```text
poiProvider: "amap"
poiId: string
poiTypeCode?: string
district?: string
adcode?: string
citycode?: string
coordinateSource: "amap_poi" | "amap_geocode" | "map_url" | "manual"
locationStatus: "verified" | "geocoded" | "needs_confirmation"
```

现有字段的语义固定为：

- `name`：官方地点名；
- `address`：官方地址；
- `city`：城市；
- `category`：产品分类；
- `coordinate`：内部统一为 `{ lat, lng }`；
- `notes`：成员备注；
- `suggestedDuration`：预计停留时间。

后续如果发现“地点”和“活动”语义仍然混淆，再增加：

```text
activityTitle?: string
```

AI 行程项必须优先保存 `placeId`，不能只保存 `placeName` 后依赖字符串匹配。

### 5.4 降级规则

| 情况 | 产品行为 |
|---|---|
| 没有 Key | 显示地图搜索不可用，允许手动添加 |
| 高德超时/限流 | 保留用户输入，转入手动添加 |
| 候选没有 POI ID | 允许改用关键词搜索或手动添加 |
| 只有地址 | 可以地理编码，但标记为需要确认 |
| 只有地图链接 | 尝试解析名称/坐标，并保留原链接 |
| 坐标不可靠 | 不参与最优路线，只作为普通地点 |
| 海外行程 | 不强行调用高德，使用现有地图链接和手动流程 |

## 6. 10 天行程主视图

建议结构：

```text
行程名称                         [查看总览]

[D1 8/1] [D2 8/2] [D3 8/3] ... [D10 8/10]

D3 · 槟城老城                     [当天路线]
今日重点：集中在老城区，下午不跨区折返
4 个地点 · 通勤约 38 分钟 · 节奏正常

09:30  乔治市壁画街                 停留 1 小时
       ↓ 约 12 分钟
10:45  姓周桥                       停留 1 小时
       ↓ 约 8 分钟
12:00  午餐                         停留 1.5 小时

[打开当天路线]                 [重新整理]
```

规则：

- 日期条完整覆盖 10 天；
- 默认只展开一个日期；
- 旅行进行中默认进入今天；
- 旅行未开始默认进入第一个未完成日；
- URL 带 `date=YYYY-MM-DD`，刷新后保留日期；
- 每天显示 3–5 个重点地点；
- 备注、投票理由、来源成员收进详情；
- 未安排地点单独展示；
- 可靠坐标显示真实通勤时间；
- 不可靠坐标显示估算或待确认；
- 管理行程、删除日期和复杂编辑不作为默认入口。

每天应有以下状态之一：

```text
未生成
已有草稿
有冲突
位置待确认
已确认
```

AI 或手动生成不能只返回有活动的日期。10 天日期骨架应完整存在，没有安排的日期也要显示“当天尚未安排”。

## 7. 最小路线算法

### 7.1 前提

- 只有可靠坐标的地点参与真实路线排序；
- 酒店有可靠坐标时作为每天默认起点；
- 默认驾车，可选步行；
- 公交先不作为第一版自动优化主模式；
- 没有地图数据时使用直线距离 fallback，但必须标记为估算。

### 7.2 处理步骤

1. 按城市和区域分组，减少跨城折返。
2. 保留已锁定活动的日期和相对位置。
3. 根据“一定要去”、正向投票和反对票生成优先级。
4. 按节奏控制每天约 3、4、5 个地点。
5. 获取地点间距离和通勤时间矩阵。
6. 用最近邻生成初始顺序。
7. 用 2-opt 减少绕路。
8. 对锁定活动之间的未锁定片段分别优化。
9. 将真实通勤时间写回每天路线。
10. 校验时间冲突和是否太赶。

### 7.3 约束

- `一定要去` 不应被静默删除；放不下时进入未安排区并提示。
- 有多个反对票的地点降低优先级，但不自动删除。
- 酒吧在“最后喝酒”偏好下放到晚间最后。
- 餐饮可以优先进入午餐或晚餐段，但没有营业时间数据时不能声称一定营业。
- 锁定活动不能被重新整理覆盖。
- 不能为了追求路线距离而违反固定活动时间。
- 每天超过 5 个地点时显示太满风险。

### 7.4 路线数据

建议为行程项增加可选字段：

```text
travelMinutesFromPrevious?
travelDistanceMeters?
travelMode?
travelSource?: "amap" | "estimated"
```

每天增加：

```text
routeStatus?: "fresh" | "estimated" | "missing"
totalTravelMinutes?
paceStatus?: "normal" | "tight" | "conflict"
```

只保存分钟数、距离和更新时间，不保存完整路线 polyline，避免 JSON workspace 过大。

## 8. 尚未解决、需要新增功能的事项

### P0：数据正确性

1. 新建行程增加目的地和时区，不再继承 seed 默认值。
2. 地点保存官方名称、地址、坐标和 POI ID。
3. 地点与活动标题分离。
4. AI 使用稳定 `placeId`，不再依赖名称匹配。
5. 10 天日期骨架完整生成。
6. 手动和历史地点支持补全、确认和合并。

### P1：旅行硬约束

1. 固定活动和不可移动时间块。
2. 抵达、离开、入住、退房时间。
3. 每天酒店或住宿位置。
4. 交通方式偏好。
5. 对无营业时间数据的地点明确显示未知。

### P1：协作和执行

1. 首页下一步行动卡片。
2. 未投票、未查看草稿、存在冲突的提示。
3. 最近变更和未读状态。
4. 出发前刷新当天路线。
5. 跳过地点、临时活动和仅解锁某一天。

### P2：数据增强

1. 营业时间和闭店提醒。
2. 公交路线。
3. 天气、票务和预订。
4. 行程结束后的真实执行反馈。

## 9. 实施顺序

### 第 0 步：先修数据与上下文基线

不先接高德，先修正：

- 新建行程目的地没有独立输入的问题；
- 新行程继承 seed 目的地和时区的问题；
- 地点官方信息与用户备注的字段语义；
- AI 行程项使用稳定 `placeId` 的契约；
- 每天日期骨架和空白日状态；
- 旧数据兼容和数据校验。

这一阶段的目标不是让界面更漂亮，而是确保后续高德搜索和路线算法有正确的城市、日期和地点身份。如果这一步不做，高德接入后仍可能对错误城市搜索、把同名地点混在一起，后续需要返工。

### 第 1 步：地点搜索闭环

- 建立 `MapProvider` 适配层；
- 实现高德输入提示和 POI 详情；
- 改造地点添加弹窗；
- 增加重复地点检测；
- 保留手动降级；
- 让酒店位置复用同一搜索组件。

### 第 2 步：10 天单日视图

- 日期条；
- 单日默认展开；
- 每日空状态；
- 重点活动；
- 通勤时间和导航入口；
- 未安排地点区。

### 第 3 步：路线和 AI 整理

- 高德路线/距离适配；
- 路线矩阵缓存；
- 最近邻 + 2-opt；
- 锁定活动保护；
- 三个结构化 AI 偏好；
- 生成后直接应用一个草稿。

### 第 4 步：协作和旅行中执行

- 下一步行动卡片；
- 未读变化；
- 出发前刷新路线；
- 跳过和临时活动；
- 仅解锁当天。

## 10. 第一阶段验收标准

### 地点

- 10 个国内关键词测试中，候选都有官方名称和可用地址；
- 选择候选后无需填写地址即可保存；
- 能保存 POI ID、坐标和城市；
- 相同 POI 不会重复添加；
- 高德不可用时仍可手动添加；
- 手动地点明确标记为未确认。

### 行程

- 10 天日期入口完整显示；
- 默认只显示一天；
- 每天最多突出 3–5 个地点；
- 选中日期后刷新不会丢失；
- 每个可靠地点有导航入口；
- 没有可靠坐标时不声称路线最优。

### AI 和路线

- AI 只生成一个当前草稿；
- AI 输出能够关联稳定 `placeId`；
- 锁定活动不会被重新整理覆盖；
- 路线时间来自地图服务或明确标记为估算；
- 时间冲突和过满风险可见。

### 兼容和安全

- 旧行程可以正常加载；
- 新增字段均为向后兼容的可选字段；
- 地图 Key 只在服务端；
- 高德失败不会阻断地点、投票和行程查看；
- 不把地图原始响应和私密资料发送给 AI。

## 11. 主要风险

| 风险 | 处理方式 |
|---|---|
| 高德额度或限流 | 缓存、限速、超时和手动 fallback |
| Vercel 到高德网络不稳定 | 服务端健康检查，失败不阻断主流程 |
| 同名 POI 或分店混淆 | 必须点选候选并保存 POI ID |
| 高德坐标与其他地图混用 | 记录坐标来源，国内默认高德导航 |
| AI 生成错误地点 | 只接受已知 `placeId`，未知项标记待确认 |
| 路线数据过期 | 保存更新时间，出发前重新计算 |
| 10 天地点太多 | 每日 3–5 个重点，其余进入未安排区 |
| 工作流过于复杂 | 前端合并收集/表态，减少强制阶段 |
| 旧数据质量差 | 提供补全、确认和合并工具 |

## 12. 当前建议的第一步

第一步不是申请高德 Key，也不是先重做行程页面。

建议先做：

> **建立“行程上下文 + 地点数据 + AI 关联”的兼容数据基线，并修正新建行程继承默认目的地的问题。**

具体交付物只有四项：

1. 新建行程可以保存目的地城市和正确时区；
2. 地点模型明确区分官方地点信息、用户备注和地点来源；
3. 行程项必须使用 `placeId` 关联地点；
4. 日期范围内每天都有明确的行程日状态。

完成这四项后，再进入高德搜索。原因是高德搜索需要正确城市上下文，路线优化需要可靠地点身份，10 天视图需要完整日期骨架，AI 需要稳定的地点引用。先做数据基线可以避免地图接入、AI 输出和行程页面分别返工。

本步骤完成后的最小验收场景：

```text
新建一个真实目的地的 10 天行程
→ 目的地和时区正确
→ 添加一个旧式手动地点
→ 明确显示位置未确认
→ 生成一个行程项并绑定 placeId
→ 10 个日期全部存在
→ 没有安排的日期显示空状态
```

这一步通过后，才开始实现高德搜索选点闭环。
